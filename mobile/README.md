# SAI for iOS

The phone app: a Vite web build of the shared SAI chat UI, inside a
Capacitor 8 iOS shell (Swift Package Manager, no CocoaPods).

| Path | What |
| --- | --- |
| `../capacitor.config.ts` | Capacitor config (`appId com.project96.sai`, `webDir dist/mobile`, `ios.path mobile/ios`) |
| `vite.config.ts` | Phone web build → `dist/mobile`. Fails the build if anything imports `electron` or a Node built-in. |
| `index.html`, `src/` | Phone entry (`html[data-sai-phone]`; `__MOBILE__` is `true`) |
| `ios/` | Xcode project, committed. Generated by `npx cap add ios`, then edited (below). |

## Build

```sh
npm run build:mobile   # web build only → dist/mobile
npm run build:ios      # web build + `cap sync ios` (copies the web build, rewrites CapApp-SPM/Package.swift)
```

`cap sync` works on Linux; compiling and signing the app needs Xcode on macOS
(CI). `ios/App/App/public` and `ios/App/App/capacitor.config.json` are
generated by sync and are not committed.

## Native edits on top of the Capacitor template

- `ios/App/App/KeychainPlugin.swift`: the local `Keychain` plugin
  (`get({key}) → {value|null}`, `set({key, value})`, `remove({key})`), generic
  passwords under service `com.project96.sai.machines`, accessible after first
  unlock. The same file holds `MainViewController`, a `CAPBridgeViewController`
  subclass that registers the plugin in `capacitorDidLoad()`;
  `SceneDelegate.swift` uses it as the root view controller. A new Swift file
  must also be added to `App.xcodeproj/project.pbxproj` (file reference, App
  group, Sources build phase).
- `ios/App/App/Info.plist`: version from `MARKETING_VERSION` /
  `CURRENT_PROJECT_VERSION`, no non-exempt encryption, camera usage (pairing
  QR), status bar not view-controller based, and App Transport Security that
  allows plain HTTP to paired desktops. Desktops are reached on the LAN, by
  `*.ts.net` name or by raw tailnet IP; a raw IP can't be listed as an
  exception domain, so `NSAllowsArbitraryLoads` is on as well.

## Tests

`tests/unit/mobile` and `tests/integration/mobile` are picked up by the normal
`npm run test:unit` / `npm run test:integration`. The phone e2e (the built app
against a fake desktop) is `npm run build:mobile && npx playwright test --config
playwright.mobile.config.ts`; it emulates an iPhone 15 in Chromium, or WebKit
with `SAI_E2E_BROWSER=webkit`. `test.yml` runs all of these on Linux.

## Release

CI is `.github/workflows/ios.yml` (macOS runner, Xcode).

- Pull requests touching the phone app compile it for the simulator, unsigned.
- To ship: set `mobileVersion` in the root `package.json`, then push the tag
  `mobile-v<x.y.z>`. The workflow archives the app, signs it at export (Xcode
  cloud-managed distribution signing) and uploads it to App Store Connect; it
  reaches TestFlight once processing finishes. The version is the tag's; the
  build number is minutes since the Unix epoch. Desktop releases use `v*` tags
  and never trigger this workflow.
- Manual run: Actions > iOS > Run workflow; untick `upload` to only compile.

Without all four secrets the workflow only compiles for the simulator and
warns.

| Secret | Value |
| --- | --- |
| `APP_STORE_CONNECT_KEY_ID` | Key ID of an App Store Connect API key (Admin role) |
| `APP_STORE_CONNECT_ISSUER_ID` | Issuer ID shown above the key list |
| `APP_STORE_CONNECT_KEY` | The `.p8` file's contents |
| `APPLE_TEAM_ID` | Apple Developer team ID |

### One-time App Store Connect setup

1. Create the API key (Users and Access > Integrations > App Store Connect
   API, Admin) and set the four secrets on `darkharasho/sai`.
2. Create the app record: My Apps > New App, iOS, bundle ID
   `com.project96.sai` (register the identifier first if it isn't listed).
3. TestFlight > Internal Testing: create a group, add testers, and enable
   automatic distribution of new builds.
