# Task Rail Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A persistent per-chat task view for Claude SDK chats, with one card per task. Each card shows the step, progress, a live tail, and waiting-on-you state, and has an isolated full-chat stream view. Two layouts (Rail / Tabs) sit behind a setting.

**Architecture:** Task state is **derived, not stored**. The model declares and updates cards with a new SDK-only `sai_task` tool. Its calls persist in chat history like any other tool call, so a pure fold over `messages` rebuilds the cards. The persistence, per-chat scoping and restart survival in the spec come free from that. Runtime truth (background task snapshots, the streaming flag, pending questions, agent transcripts) is merged in at render time and is display-only. Agent transcripts are read on demand from disk through the SDK's `getSubagentMessages`. They are matched by the Agent call's `tool_use` id, which is recorded in each agent's `.meta.json`.

**Tech Stack:** Electron, React 19, TypeScript, `@anthropic-ai/claude-agent-sdk`, vitest + Testing Library.

**Spec:** `docs/superpowers/specs/2026-11-10-task-rail-design.md` (mockups: `2026-11-10-task-rail-mockup.png`, `2026-11-10-task-rail-options.png`)

## Global Constraints

- Run vitest with `--maxWorkers=2` (machine memory limit).
- Applies only to Claude chats on the SDK backend (`claudeBackend` setting ≠ `'cli'`, `claudeKind === 'chat'`). CLI-backend Claude chats and the Codex/Gemini/Kimi providers keep today's UI unchanged, including `BackgroundTasksSidebar` and `TodoProgress`.
- The task board is display-only. It never feeds turn completion, notifications, wait/stuck state, or `turnSeq` logic.
- Don't persist large blobs. Card state is derived from `messages`; transcripts are read from disk on demand and are never written into chat records.
- Every value read from tool input or a transcript may be a non-string. Coerce before string ops (an uncaught throw blanks the whole app, as in the v1.20.9 black screen).
- Never compare filesystem paths by string equality (`/home` → `/var/home` symlink).
- Use the existing theme CSS variables (`--surface-*`, `--border-*`, `--accent`, `--blue`, `--green`, `--orange`, `--red`). Respect reduced motion. Don't use framer `layoutId` shared-element morphs.
- Setting key `taskView`, values `'rail' | 'tabs'`, default `'rail'`.
- Polling interval for live agent transcripts: `2000` ms. Poll only cards in the active chat whose agent is still running.

## Review Focus

1. **The model ignores `sai_task`** and uses TaskCreate/TodoWrite, or nothing. Expect the fallback "Current work" card, or no rail at all. Never an empty rail, never a crash. *(Task 4 test `fallback card from TodoWrite when no sai_task calls`; Task 4 test `no cards and no rail data when chat has neither`.)*
2. **Malformed `sai_task` input**: an update for an unknown id, `step` out of range, duplicate ids in one create, non-string titles, unparseable JSON. Expect the bad call to be ignored and the rest of the board to stay correct. *(Task 3 test `ignores malformed calls without throwing`.)*
3. **The `agent` string doesn't match any Agent call or background task.** Expect the declared card to stay as an inline card and the agent to appear as its own runtime card. Nothing should disappear. *(Task 4 test `unmatched agent string yields declared card plus runtime card`.)*
4. **Transcript unavailable** (deleted session, missing meta, IPC rejects). Expect an empty tail and "Transcript unavailable" in the stream view, with no crash and no retry storm. *(Task 5 test `returns null when no meta matches`; Task 8 test `shows unavailable state when transcript is null`.)*
5. **Switching chats or restarting mid-run.** Expect running inline cards to show **paused** once streaming has stopped, and polling for the old chat to stop. *(Task 4 test `running inline card is paused when not streaming`; Task 5 test `stops polling on unmount and when ids go non-live`.)*

### Task 3: Declared-card fold

**Files:**
- Create: `src/components/Chat/tasks/declaredCards.ts`
- Test: `tests/unit/components/Chat/tasks/declaredCards.test.ts`

**Interfaces:**
- Consumes: `TaskCard`, `SaiTaskInput` (Task 1); `isSaiTaskToolName`, `validateSaiTaskInput` (Task 2).
- Produces: `deriveDeclaredCards(messages: ChatMessage[]): { cards: TaskCard[]; batchStartedAt: number | null; activeInlineId: string | null }`

Rules (the fold walks assistant `toolCalls` in order, using `message.timestamp` as event time):

**create**
- If there is no current batch, or every card in it is `done`/`failed`, start a **new batch**: drop the old cards and set `batchStartedAt`.
- Otherwise append to the current batch.
- Duplicate ids within the batch are skipped.
- New cards are `queued`, with all steps `pending`.

**update** (unknown id → ignore)
- `status: 'running'` with `step: k`:
  - Clamp `k` to `[0, steps.length - 1]`.
  - Steps before `k` become `done`, step `k` becomes `current`, and `startedAt` is set if still null.
- `status: 'running'` with no `step`: `step` defaults to the current index, or 0.
- `status: 'done'`: all steps become `done`; set `endedAt` and `result = note`.
- `status: 'failed'`: keep the steps, set `endedAt`, and `result = note ?? 'Failed'`.
- `add_steps`: append the new steps as `pending`.
- `agent`: set `card.agent = { description: agent, toolUseId: null, taskId: null }`.

**Inline attribution**
- `activeInlineId` is the most recent card set to `running` that has no `agent`.
- It clears when that card turns `done`/`failed`, or when another card is set `running`.
- Every assistant message after the call that set it is appended to that card's `messageIds`, except messages whose only tool calls are `sai_task` and whose text is empty. Messages from before or between active cards are not attributed.

**Derived fields**
- `doneCount`, `totalCount` and `currentLabel` (the label of the `current` step) are computed at the end.

**Robustness**
- Invalid or unparseable input → skip the call.
- Never throw.

  - `running with step marks earlier steps done`: `step: 2` of 5 → `doneCount 2`, `currentLabel` equal to step[2].
  - `done sets result and endedAt; failed keeps steps`.
  - `create after all done starts a new batch; create while one running appends`.

### Task 4: Board merge with runtime truth (+ `toolUseId` on background tasks)

**Files:**
- Create: `src/components/Chat/tasks/taskBoard.ts`
- Modify: `electron/services/claudeBackend/backgroundTasks.ts`. Add `toolUseId: string | null` to `BackgroundTaskDetail` (`blank()` sets null; `task_started`/`task_progress` set it from `frame.tool_use_id` when it's a string).
- Test: `tests/unit/components/Chat/tasks/taskBoard.test.ts`, `tests/unit/backgroundTasks.test.ts` (extend; find the existing fold test with `grep -rl foldBackgroundTaskFrame tests`)

**Interfaces:**
- Consumes: `deriveDeclaredCards` (Task 3), `findLatestTodos` (`TodoProgress.tsx:21`), `BackgroundTaskDetail`.
- Produces:
```ts
export interface BoardRuntime {
  backgroundTasks: BackgroundTaskDetail[];
  isStreaming: boolean;
  pendingQuestion: { text: string; options: string[] } | null;
  agentInfo: Map<string, { finished: boolean; steps: TaskStep[] }>; // keyed by toolUseId, from Task 5
}
export function deriveTaskBoard(messages: ChatMessage[], rt: BoardRuntime): TaskBoard
export function agentToolUseIds(board: TaskBoard): string[]   // cards whose agent.toolUseId is known
```

Merge rules:

1. **Resolve each declared card's `agent.toolUseId`.**
   - First, find the `Agent` tool call in `messages` whose parsed `input.description === agent.description`; its id is the `toolUseId`.
   - Otherwise, use a background task whose `description` equals it, and take its `toolUseId`/`id`.

2. **Agent-backed declared card status.** Look up the matching background task by `toolUseId`.
   - If it's `running`/`pending`/`paused`, the card is `running`.
   - If it's `completed`, the card is `done`.
   - If it's `failed`/`stopped`, the card is `failed` (stopped → result `'Stopped'`).
   - If there is no detail but `agentInfo.get(toolUseId)?.finished` is true and the model hasn't declared `failed`, the card is `done`.
   - If there is no detail and it isn't finished but the model said `running`, the card is `paused`.
   - Runtime overrides the model's claim in every case above.
   - When `steps` is empty and `agentInfo` has steps, use those.

3. **Inline declared card** (no agent), declared `running`: it is `paused` if `!isStreaming`. If `pendingQuestion` is set and this is `activeInlineId` (or, when there is none, the first running inline card), it is `waiting` with `question = pendingQuestion`.

4. **Runtime cards.** Each non-hidden background task not matched in step 1 becomes a card:
   - `id: 'bg:' + task.id`, `source: 'runtime'`, `title: description || kind`
   - status mapped as in rule 2
   - `agent: { description, toolUseId: task.toolUseId, taskId: task.id }`
   - steps from `agentInfo` or `[]`
   
   Order: declared cards first, then runtime cards by `startedAt`.

5. **Fallback.** If there are no declared cards and `findLatestTodos(messages)` returns at least one item, add one card:
   - `id: 'current-work'`, `source: 'fallback'`, `title: 'Current work'`
   - steps from the todos (`completed` → `done`, `in_progress` → `current`)
   - status `done` if every todo is completed, otherwise `running` (`paused` when not streaming)

6. `allDone` = there is at least one card, and every card is `done`/`failed`.
